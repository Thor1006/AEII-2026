# Plan B: Evaluate AWR2944PEVM without DCA1000

**Status:** Plan B selected; hardware not ordered
**Date:** 2026-10-18

This is the detailed implementation plan for **Plan B** in [the hardware procurement options](2026-10-18-hardware-procurement-options.md). Plan A (Acconeer XE125) uses a different radar, SDK and data interface and must not be implemented from this firmware plan.

## Why

The submitted AEII poster and proposal name AWR1843BOOST with DCA1000EVM, but both boards are difficult to obtain within the remaining schedule. AWR2944PEVM may be deliverable sooner. The implementation plan therefore needs a documented contingency that does not rewrite the already-submitted poster or pretend that software alone is equivalent to DCA1000.

## Decision boundary

- **Submitted design (frozen):** AWR1843BOOST + DCA1000EVM, with raw ADC/I-Q capture for offline processing.
- **Selected implementation:** AWR2944PEVM without DCA1000EVM throughout Plan B. DCA1000, its dedicated supply and capture cable are excluded, including deferred upgrades.
- **Procurement status:** selected but not ordered until the team confirms an order and delivery date.
- **Technical limitation:** normal PC code cannot replace DCA1000's FPGA, LVDS/Aurora capture, buffering, and sustained Ethernet packetization.

## Recommended architecture

```text
AWR2944P RF/ADC
  → ADC buffer
  → EDMA + HWA/C66x processing on the radar SoC
  → Range FFT and Doppler/angle processing
  → select a reduced output
  → R5F packetization and Ethernet
  → notebook Python receiver
  → recording, signal analysis, AI and dashboard
```

Develop outputs in this order:

1. TI Out-of-Box detected objects/point cloud, to prove board, radar and Ethernet operation.
2. Range profile or reduced Range-Doppler representation, for movement analysis and the existing CNN interface.
3. Selected complex Range-FFT bins around a tracked body region, to preserve phase for exploratory micro-motion analysis.

Continuous full raw ADC streaming without DCA1000 is not an initial deliverable. It may be researched later, but only after measuring ADC format, data rate, memory use, processing deadline and Ethernet throughput.

## Firmware principles

- Start from the AWR2944P-compatible Out-of-Box/Ethernet demo in TI MMWAVE-MCUPLUS-SDK; do not port the AWR1843 application blindly.
- Use Embedded C/C++ on the EVM.
- Use HWA/C66x for radar processing, EDMA for data movement and R5F for control/network output.
- Keep radar callbacks short. Do not perform blocking Ethernet sends inside an ADC/chirp interrupt.
- Use preallocated ping-pong buffers and a producer/consumer queue.
- Give every transmitted frame a version, frame number, radar timestamp, payload type, dimensions, chunk number/count, payload length and integrity check.
- Keep UDP payloads below the path MTU and reconstruct complete frames on the PC. Detect missing, duplicated and out-of-order chunks.
- Record the complete radar configuration and data-layout version with every session.

## PC software principles

- Python receives and validates Ethernet/UDP packets, reconstructs frames and records packet-loss information.
- Store numerical data plus timestamps and configuration metadata; do not use screenshots as the dataset.
- Keep acquisition/disk writing separate from visualization so the dashboard cannot block recording.
- Preserve identical preprocessing between training and live inference.
- If selected complex bins are available, perform ROI tracking, phase unwrapping, clutter/motion rejection and filtering before extracting fatigue-related features.
- Validate with reference labels; radar output alone is not proof of muscle fatigue or compensation.

## Minimum viable result

1. Power, flash and run the unmodified AWR2944PEVM OOB demo.
2. Detect a controlled stationary and moving target.
3. Receive continuous numbered data on the notebook and measure loss/runtime.
4. Feed a documented radar representation into the existing dashboard or replay path.
5. Only then attempt custom Range-Doppler or selected-complex-bin output.

## Hardware/software needed

- AWR2944PEVM.
- MEAN WELL GST60A12-P1J or another verified 12 V supply with more than 2.5 A capability, following the EVM guide. Confirm connector fit and polarity before use.
- USB cables required for flashing/debug/configuration.
- Ethernet cable and notebook Ethernet interface.
- TI MMWAVE-MCUPLUS-SDK, its documented CCS/SysConfig versions, flashing tool, Wireshark and the Python processing environment.

## Risks / needs OK

- Do not purchase hardware based only on the existence of Ethernet; confirm stock, delivery and required accessories.
- The standard Ethernet demo may expose detected objects rather than raw ADC or the exact intermediate tensor wanted by the ML pipeline.
- Custom firmware could consume more than the remaining schedule. Preserve the OOB-demo path as the fallback demonstration.
- The submitted poster remains unchanged; presentations must clearly label the AWR2944PEVM path as a prototype substitution.

## How we'll verify

- Build/flash the SDK example before modifying its data path.
- Verify target range and motion with controlled tests.
- Log actual frame rate, payload rate, packet loss, dropped frames and continuous runtime.
- Freeze the real output shape and preprocessing in the model `InputContract` only after a real capture.
